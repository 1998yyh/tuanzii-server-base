# 新数据扫描后联动观察池 S 评估

日期：2026-11-09。分支：`feature/scan-watchlist-evaluation`。

## 行为

此前扫描接口只写入信号；观察池依赖入池检查、手动历史检查或 10:00 / 14:50 定时任务，导致用户强制重扫取得新 S 后，观察池仍显示持续观察。

现在 `StockSignalsService` 在指定代码同步扫描和全市场异步扫描的新数据成功落库后，按成功取数的代码查找全站 `watching` 条目，并使用共享 `evaluateWatchlist` 规则评估。全市场任务在评估完成后才发布 `done`，无需前端保持打开。并非仅 `refresh=true` 才联动：首次无缓存扫描的新取数也会联动。

- 全部命中缓存、不取数或全部取数失败时，不评估观察池。
- 部分失败时，仅评估成功取数的股票，失败代码继续按原接口报告。
- 新信号写库失败时不评估；后续观察池评估异常会使同步扫描返回错误，或使异步任务标记失败，不会提前发布 `done`。
- S 条件保持同代码、`value='0'`、`入池依据日 < signal_date <= 上海今天`，取符合条件的最大日期；已触发项锁定。条件更新保留用户归属及旧状态，避免并发重复触发或更新已删除条目。
- 新扫描只重新抓取所选扫描日期，评估使用本次写入与数据库已确认历史。不会在此额外请求每只股票的全部历史；观察池“立即检查”继续提供完整历史补查。

## 实现与兼容

新增 `src/stock-signals/evaluate-watchlist.ts` 复用原 S 判定，`WatchlistService.evaluateWatching` 改为委托它；`StockSignalsService` 增加已有 `StockWatchlist` Repository 注入，避免两业务 Service 循环依赖。股票模块原本已注册该实体，无新增模块、依赖、配置、接口字段或 DDL。

循势前端 `useSignals` 通过完成回调通知 `SignalWorkspace` 重新读取个人观察池；读取复用既有身份代际与取消保护，失败仍显示原观察池错误提示。仅同步 GET，不再重复请求历史检查。异步任务完成/刷新恢复均同步，指定代码仅有新取数时同步；普通缓存查询不增加观察池请求。
